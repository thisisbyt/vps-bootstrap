# Текущее reference-окружение

Этот файл описывает известное текущее окружение пользователя и нужен агенту как контекст.

**Важно:** значения ниже не являются автоматическими pinned versions для новых установок. Перед реализацией модуля установки версии должны быть вынесены в `versions.yml` и отдельно подтверждены как поддерживаемые.

## VPS

Primary target проекта:

```text
Ubuntu 24.04 LTS
```

Ubuntu устанавливает хостер до запуска VPS Bootstrap.

Старые reference-установки могли использовать Ubuntu 22.04, но v0.1.2 целится в Ubuntu 24.04 LTS. Это сознательное решение и не должно откатываться автоматически.

Известные компоненты текущего окружения:

```text
3x-ui: 2.4.11
Xray server core: 25.2.18
```

При проектировании новой установки 3x-ui:

- предпочтителен PostgreSQL, если выбранная версия панели его поддерживает;
- SQLite не следует считать обязательной или предпочтительной БД;
- installation module должен учитывать различия между версиями панели.

## Домашний роутер

Используется Keenetic с XKeen.

Reference versions:

```text
XKeen: 1.1.3
Xray client on router: 25.2.18
```

На роутере используется Xray-клиент для маршрутизации трафика через VPS.

## Известная особенность XKeen/DNS

Наблюдался сценарий:

- при работающем XKeen обычные UDP DNS-запросы могли получать два таймаута;
- TCP DNS при этом работал быстро;
- при полном `xkeen -stop` UDP DNS начинал отвечать мгновенно;
- отключение отдельной функции DNS interception не устранило проблему.

Следствие для диагностики VPS:

не делать вывод "DNS на VPS сломан" только на основании проверки с клиента за XKeen. При сетевой диагностике разделять:

- VPS DNS;
- клиентский DNS;
- UDP DNS;
- TCP DNS;
- DNS routing через XKeen/Xray.

## Proxy-сценарии

Используются/рассматриваются:

- VLESS/Xray;
- 3x-ui;
- NaiveProxy;
- Caddy с forwardproxy;
- WARP как опциональный outbound/дополнительный компонент.

Порт 443 является дефицитным ресурсом и может потребоваться одновременно нескольким компонентам. Любой module, затрагивающий 443, обязан сначала определить текущего владельца порта.

## Monitoring

Из предыдущей конфигурации используется подход с лёгким executable:

```text
/usr/local/bin/vps-monitor
```

Monitoring должен:

- иметь небольшой runtime/RAM overhead;
- контролировать ресурсы и critical services;
- отправлять alerts через Telegram;
- не раскрывать Telegram token в логах.

Предпочтительный scheduler для нового проекта — systemd timer, если нет отдельной причины использовать cron.

## Ресурсные ограничения

Часть VPS может иметь небольшой объём RAM/disk.

В эксплуатации уже встречались:

- заметное потребление RAM дополнительными daemon, включая WARP;
- значительное использование swap;
- заполнение root filesystem до 100%;
- рост systemd journal.

Поэтому disk/RAM/swap/journal checks относятся к базовым, а не дополнительным функциям monitoring.

## Публичный IP и безопасность

VPS имеет публичный IP по своей природе; также в домашней инфраструктуре используется публичный адрес.

Основной подход:

- минимальный attack surface;
- UFW;
- Fail2ban;
- SSH hardening;
- не публиковать PostgreSQL;
- management UI не выставлять наружу без необходимости;
- отдельная проверка listening ports после provisioning.
