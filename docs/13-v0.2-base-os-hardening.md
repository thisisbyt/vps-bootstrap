# v0.2.0 Base OS Hardening

v0.2.0 completes the base OS preparation layer for Ubuntu 24.04 LTS. It does not install Xray, 3x-ui, PostgreSQL, NaiveProxy, Caddy, WARP, Docker, Telegram monitoring, VPN service ports, or aggressive sysctl tuning.

## Phase Order

`full` uses this order:

```text
preflight
runtime_directories
logging
config
time_sync
swap
admin_user
root_hardening
firewall
fail2ban
ssh_hardening
security_updates
journald_structure
ansible_foundation
```

`base` remains conservative and does not run `swap`, `admin_user`, `root_hardening`, `firewall`, `fail2ban`, or `ssh_hardening`.

## Admin User

The `admin_user` phase creates or validates a non-root sudo user. It rejects `root` and system UIDs, validates Linux usernames, accepts SSH public keys only, and never stores passwords, password hashes, private keys, or private key paths.

Existing accounts must meet the system `UID_MIN` normal-user policy. Ownership checks and repairs use the account's numeric UID and primary GID. Existing option-prefixed `authorized_keys` entries are preserved and deduplicated by key identity, so a restricted key is never duplicated as an unrestricted entry.

Sudo authentication is an explicit choice:

1. Password-required sudo (recommended) uses the system `passwd` program with the terminal inherited. Python does not receive or capture the password.
2. Passwordless sudo creates only `/etc/sudoers.d/10-vps-bootstrap-admin` with an exact-user `NOPASSWD` rule. It never changes `%sudo`, package-owned `/etc/sudoers`, or `@includedir`.

The NOPASSWD drop-in is atomically written as `root:root 0440` and the complete sudoers configuration is validated with `visudo -cf /etc/sudoers`. A failed validation restores the previous managed file or its proven absence. Switching back removes only this managed drop-in. For an existing account without a usable local password, password-required mode blocks before removing NOPASSWD unless the user explicitly chooses to run `passwd`.

Local account password policy is separate from sudo convenience. A new NOPASSWD admin can either set a recovery/console password (recommended) or keep the password locked for SSH-key-only access. Existing account passwords are never changed or locked merely because NOPASSWD was selected.

The managed state stores only non-secret fields:

```text
username
public key fingerprint
validation flag
sudo mode and validation flag
local-password status/policy (never the password or hash)
```

The phase is not considered safe until the user confirms a real second SSH session using publickey-only authentication and verifies sudo. The SSH client must use the private key corresponding to the configured public key. For a non-default key that is not already selected by `ssh-agent` or OpenSSH config, the instructions use a client-side placeholder:

```bash
ssh -i <path-to-private-key> -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no admin@203.0.113.10
```

The user replaces the placeholder locally. When the corresponding key is already selected by `ssh-agent`, OpenSSH config, or a default identity, `-i` and `IdentitiesOnly=yes` may be omitted. vps-bootstrap never discovers, stores, or logs a client-side private-key path.

Password-required sudo mode uses:

```bash
sudo -k
sudo -n true  # expected to fail before authentication
sudo -v
sudo -n true
echo $?       # must print 0
```

The first non-interactive command is expected to fail and proves that no unexpected NOPASSWD policy bypasses authentication. This expected failure is part of the validation, not a bootstrap failure. `sudo -v` must then perform normal authentication, and the final non-interactive command must succeed.

NOPASSWD mode validates the opposite policy without `sudo -v`:

```bash
sudo -k
sudo -n true
sudo -n whoami
```

The final command must report `root`.

The same selected sudo-mode sequence is shown again immediately before `PermitRootLogin no` is finalized. NOPASSWD never invokes `sudo -v`; password-required mode retains the expected pre-authentication failure followed by authenticated success.

Root/password SSH remains available until the alternative admin path is validated.

## Root Hardening

`root_hardening` runs only after `admin_user` verifies the alternate publickey and sudo path.

The root authorized-key audit parses ordinary and option-prefixed OpenSSH public-key lines, then displays only index, key type, SHA256 fingerprint, optional comment, and whether restrictions are present. The user may remove all keys (recommended), select keys to retain, or keep the file unchanged. Before modification, the exact original file is copied to a unique root-only backup. Key bodies are never stored in InstallState or logs. Unparseable non-comment material blocks automatic cleanup.

Removing `/root/.ssh/authorized_keys` affects credentials inside the guest OS only. It does not remove provider hypervisor, rescue, serial-console, or VNC control.

Root local-password policy is independent of SSH keys and sudo mode. If the admin has a verified local password, the default is `passwd -l root`. If the admin has no usable local password, the default is to preserve root's password and warn that locking it would remove the normal password-based console recovery path. The phase verifies `passwd -S root`. It never changes root's shell, expires the account, disables UID 0, or silently unlocks root on reconfiguration, so `sudo -i` and `sudo -s` remain available.

The legacy `admin` group is audit-only. Membership includes supplementary members and accounts whose primary GID is the group's GID. If non-root members receive sudo through `%admin`, their usernames are reported. vps-bootstrap does not delete the group or edit package-owned sudoers policy.

## UFW Firewall

The `firewall` phase manages UFW with:

```text
default deny incoming
default allow outgoing
allow current SSH TCP port(s)
```

It never runs `ufw reset`, does not open 80/443 or future application ports, and preserves unrelated rules. vps-bootstrap-managed SSH rules use an identifiable comment:

```text
vps-bootstrap:ssh
```

Later components should request managed ports through the firewall module rather than resetting user rules.

## Fail2ban

The `fail2ban` phase manages only SSH protection through:

```text
/etc/fail2ban/jail.d/10-vps-bootstrap-sshd.local
```

Recommended preset:

```text
maxretry = 5
findtime = 10m
bantime = 1h
backend = systemd
port = actual current SSH port(s)
```

Customize mode allows `maxretry`, `findtime`, `bantime`, and optional `ignoreip` entries. It does not expose low-level jail internals by default and does not automatically whitelist the administrator's current public IP.

## SSH/UFW/Fail2ban Transaction

When SSH migrates from OLD_PORT to NEW_PORT and managed UFW/Fail2ban exist, the transaction is:

1. Add managed UFW allow for NEW_PORT.
2. Configure SSH for OLD_PORT + NEW_PORT.
3. Verify actual SSH listeners.
4. Configure managed Fail2ban sshd jail for OLD_PORT + NEW_PORT.
5. Require a real second SSH session on NEW_PORT.
6. If auth hardening is requested, require publickey-only validation.
7. If root SSH disable is requested, require validated non-root sudo access.
8. Finalize SSH to NEW_PORT only.
9. Verify NEW_PORT listener.
10. Update Fail2ban to NEW_PORT only.
11. Remove only the vps-bootstrap-managed OLD_PORT UFW rule.
12. Perform final verification.

If UFW cleanup fails, leaving an extra managed allow rule is safer than risking SSH access. Unrelated firewall rules are never deleted.

Rollback first restores and verifies the OLD_PORT firewall path, then restores and verifies the OLD_PORT SSH listener, then restores Fail2ban. Temporary NEW_PORT firewall access is removed only after those safety-critical steps succeed. If SSH or Fail2ban rollback fails, NEW_PORT access remains allowed and the migration stays interrupted for explicit recovery.

The Fail2ban transaction keeps one immutable pre-migration jail backup. Finalization uses separate operation backups and cannot overwrite that rollback snapshot. Effective verification rejects conflicting external `[sshd] port` overrides without using the unsupported `fail2ban-client get sshd port` command.

If UFW or Fail2ban are absent or unmanaged, SSH follows the v0.1.3 no-UFW/no-Fail2ban path.

The final managed authentication policy explicitly verifies:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PermitEmptyPasswords no
```

`PermitEmptyPasswords` is discovered from `sshd -T`, rendered in the managed drop-in, and included in candidate and final effective verification. No `AuthenticationMethods` value is introduced.

## Security Updates

The `security_updates` phase enables Ubuntu security unattended upgrades, verifies that an Ubuntu security origin is effective, and keeps automatic reboot disabled. It reports whether a reboot is required but does not run a full upgrade on every `full` execution and does not configure automatic reboot.

Ambiguous existing unattended-upgrades policy that enables automatic reboot blocks automatic overwrite.

## Permissions

vps-bootstrap uses explicit ownership and modes instead of adding a global `umask 0077` to shell startup files.

| Managed path | Owner | Mode |
| --- | --- | --- |
| admin home | admin UID:primary GID | `0700` |
| admin `~/.ssh` | admin UID:primary GID | `0700` |
| admin `authorized_keys` | admin UID:primary GID | `0600` |
| `/root/.ssh` when present | `root:root` | `0700` |
| root `authorized_keys` when present | `root:root` | `0600` |
| root-key backup directories | `root:root` | `0700` |
| root-key backup files | `root:root` | `0600` |
| `/etc/sudoers.d/10-vps-bootstrap-admin` | `root:root` | `0440` |
| `/var/lib/vps-bootstrap` and sensitive state/backup directories | `root:root` | `0700` |
| `/var/lib/vps-bootstrap/state.json` | `root:root` | `0600` |

Non-secret SSH/systemd/service drop-ins retain service-compatible root-owned readable modes such as `0644`. Runtime release directories remain `0755`, `bootstrap.sh` remains `0755`, and ordinary runtime source/templates remain `0644`; the release tree is not treated as secret material.

## Bootstrap Dependencies

The v0.2.0 bootstrap baseline is intentionally small:

```text
ca-certificates
curl
git
openssh-client
passwd
python3
python3-venv
iproute2
sudo
```

`sudo` provides `sudo`/`visudo`, `openssh-client` provides `ssh-keygen`, and `passwd` provides the account tools used by admin/root hardening. `net-tools` is unnecessary because `ip` and `ss` come from `iproute2`. `nmap` is not installed on every VPS; an optional external scan from a separate host is a better acceptance check of the Internet-facing surface.

## Recovery

State/resume remains verification-first:

```text
DONE + verifier OK -> SKIP
DONE + verifier failed -> DRIFT/REPAIR
SKIPPED -> stable skipped state
```

Interrupted SSH migration recovery remains explicit and safety-first. Resume never removes the old SSH port automatically. Rollback success is recorded only after rollback verification succeeds.

Interrupted SSH recovery runs before ordinary firewall or Fail2ban drift handling. Successful migration or rollback synchronizes the saved `firewall` and `fail2ban` phase data with the authoritative ports established by the transaction.

## Acceptance

Minimum disposable Ubuntu 24.04 VPS acceptance:

- fresh install from v0.2.0 artifact;
- `admin-user` creates or validates non-root sudo publickey access in password-required and per-user NOPASSWD modes;
- `root-hardening` audits/backups root keys and applies the conditional root-password policy only after alternate access validation;
- explicit permission and ownership matrix is verified;
- `firewall` enables UFW without losing SSH;
- `fail2ban` protects actual SSH port;
- SSH OLD -> NEW migration with managed UFW and Fail2ban;
- second-session failure rollback;
- repeated SSH reconfiguration;
- `security-updates` enables security unattended upgrades and disables auto reboot;
- `full` is idempotent after successful setup;
- `resume` does not expand saved safe scope unexpectedly.
