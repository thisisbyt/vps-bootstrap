# AGENTS.md — правила работы над VPS Bootstrap

## 1. Назначение проекта

Этот репозиторий создаёт воспроизводимый provisioning для VPS, на котором могут быть установлены:

- базовая системная конфигурация Ubuntu;
- SSH hardening;
- UFW;
- Fail2ban;
- Xray;
- 3x-ui;
- PostgreSQL для 3x-ui, если выбранная/поддерживаемая версия панели это позволяет;
- NaiveProxy на базе Caddy с forwardproxy;
- TLS;
- опционально WARP;
- мониторинг ресурсов и сервисов;
- уведомления через Telegram-бота;
- резервное копирование конфигураций и данных;
- финальный аудит готовности сервера.

Проект должен позволять потерять VPS, заказать новый, получить Ubuntu от хостера, выполнить минимальный bootstrap и воспроизвести рабочую конфигурацию без ручного повторения десятков команд.

## 2. Главные архитектурные принципы

1. Нельзя предполагать наличие Python, Git, Ansible, curl, jq и других утилит на свежем сервере.
2. Точка входа — минимальный POSIX/Bash bootstrap, работающий на стандартной Ubuntu.
3. Bootstrap устанавливает базовые зависимости и только после этого запускает основной CLI/Ansible.
4. Основной интерфейс для пользователя — интерактивный CLI.
5. Ansible и другие внутренние механизмы являются деталями реализации; пользователь не должен быть обязан знать Ansible.
6. Любая операция должна стремиться быть идемпотентной.
7. Каждый критический шаг должен иметь отдельную проверку результата.
8. Нельзя считать команду успешной только потому, что она завершилась с exit code 0.
9. Конфигурация должна поддерживать безопасный повторный запуск.
10. Должна существовать возможность продолжить установку после исправления ошибки.
11. Все версии критических компонентов должны контролироваться централизованно.
12. Нельзя без необходимости устанавливать "latest" без фиксации/валидации версии.
13. Любая операция, способная оборвать SSH-доступ, должна выполняться только в безопасной последовательности.
14. Перед изменением работающей конфигурации необходимо создавать backup соответствующего компонента.
15. Для новых установок 3x-ui предпочтительно использовать PostgreSQL, если выбранная версия панели официально поддерживает его. Не хардкодить предположение о схеме БД: способ подключения должен зависеть от версии панели и проверяться установщиком.
16. 3x-ui admin UI MUST NOT be publicly exposed by default.
17. Time synchronization является базовой частью готовности VPS. Preflight только диагностирует time state и выдаёт WARN, если часы не синхронизированы при разумном системном времени. Base/full setup должен обеспечить фактическую синхронизацию. Наличие active NTP service не равно synchronization. При неработающем systemd-timesyncd допустим managed fallback на chrony через штатный Ubuntu apt. Каждый NTP provider проверяется независимо; failure одного provider не означает блокировку UDP/123.
18. Development repository, release artifact и installed product — разные слои. Production VPS получает только immutable versioned runtime artifact, собранный по explicit allowlist. `main` branch не является deployment artifact.
19. Development docs/instructions (`AGENTS.md`, `docs/`, `tests/`, workflow files, notes) никогда не входят в runtime artifact. Новый файл репозитория не попадает в artifact, пока его явно не добавили в packaging allowlist.
20. Release tag обязан совпадать с project version из canonical version source (`versions.yml`): tag `v0.1.2` соответствует version `0.1.2`.
21. Secrets, runtime config, state, logs, private keys и credentials никогда не входят в release artifact.
22. Runtime artifact не поддерживает symlinks. Packaging должен завершаться ошибкой при symlink manifest entry или symlink внутри allowlisted directory.
23. Production GitHub Release assets immutable: не использовать `--clobber`; изменение artifact требует новой project version и нового tag.

## 3. Правила работы с секретами

Никогда не сохранять в Git:

- Telegram Bot Token;
- Telegram Chat ID, если пользователь считает его чувствительным;
- SSH private keys;
- пароли;
- Xray UUID, если пользователь не хочет публиковать их;
- Reality private keys;
- NaiveProxy credentials;
- пароли 3x-ui;
- API keys;
- Cloudflare tokens;
- PostgreSQL credentials;
- резервные копии БД с пользовательскими данными;
- любые `.env` с реальными значениями.

Секреты должны:

- запрашиваться интерактивно непосредственно в терминале VPS;
- по возможности вводиться скрыто (`getpass`, `read -s`);
- либо генерироваться локально безопасным генератором;
- сохраняться на сервере с минимально необходимыми правами;
- не попадать в install log;
- не выводиться повторно в stdout без явной необходимости.

Если пользователю предлагается сгенерировать пароль/ключ, интерфейс должен давать выбор:

1. ввести самостоятельно;
2. сгенерировать автоматически.

## 4. Обязательное правило взаимодействия с пользователем

Если пользователю нужно что-либо выполнить вручную в локальном терминале, на VPS, в DNS-панели или в другом интерфейсе, агент обязан:

1. явно сказать, **где** выполняется действие;
2. дать **точные команды**, готовые к копированию;
3. указать, требуется ли `sudo`;
4. объяснить, какой результат ожидается;
5. добавить раздел **"Важные примечания"**, если действие:
   - может оборвать SSH;
   - меняет firewall;
   - меняет DNS;
   - изменяет порт SSH;
   - перезапускает критический сервис;
   - может повлиять на доступность VPN/прокси;
   - затрагивает БД;
   - удаляет данные;
   - меняет TLS;
   - занимает порт 80/443;
   - требует дождаться DNS propagation или другого внешнего состояния.

Нельзя писать инструкции вида "установите зависимости" без команд.

Плохо:

> Установите curl и git.

Хорошо:

```bash
sudo apt-get update
sudo apt-get install -y curl git ca-certificates
```

После команды должно быть указано, как проверить результат:

```bash
curl --version
git --version
```

## 5. Правило для опасных изменений

Перед потенциально опасной операцией агент должен:

- объяснить риск;
- выполнить pre-check;
- сохранить backup;
- подготовить rollback;
- только затем менять конфигурацию;
- после изменения проверить работоспособность.

Особенно это относится к:

- SSH;
- UFW/nftables/iptables;
- портам 22/80/443;
- сетевым маршрутам;
- DNS;
- Xray routing;
- Caddy;
- PostgreSQL;
- обновлению 3x-ui;
- обновлению Xray;
- WARP.

## 6. Работа с версиями

Версии компонентов должны быть вынесены в отдельный конфигурационный файл, например `versions.yml`.

Для каждого компонента желательно хранить:

- проверенную версию;
- минимально поддерживаемую версию;
- URL/метод установки;
- checksum, если применимо;
- дату последней проверки;
- примечания о совместимости.

Не предполагать, что текущая версия 3x-ui/Xray/Naive/Caddy/WARP остаётся актуальной навсегда.

Если установка зависит от поведения конкретной версии, код должен явно это учитывать.

## 7. Стиль реализации

Предпочитать:

- небольшие модули;
- явные функции;
- понятные имена;
- structured logging;
- отдельные проверки;
- template-файлы вместо гигантских строк в коде;
- state-файл для resume;
- dry-run/check режим там, где это возможно;
- понятные сообщения об ошибках;
- отсутствие неявных destructive-операций.

Не создавать огромный `install.sh`, содержащий всю систему.

Ожидаемая модель:

```text
bootstrap.sh
    ↓
Python CLI
    ↓
state/config
    ↓
Ansible roles / специализированные модули
    ↓
verification
```
